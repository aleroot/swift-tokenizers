# Unicode compatibility

Unicode classification and normalization follow the running Apple OS and Swift standard
library. Normalization fallbacks use Foundation's public ICU transforms, avoiding conformance
defects in NSString's precomposed/decomposed properties. Token IDs for newly assigned or reclassified
characters can therefore differ across OS versions. The library does not promise a frozen
Unicode version independent of the runtime.

Classification has no checked-in Unicode data. Two lazy 64 KiB BMP caches are built from
Swift's scalar properties. Scanners retain their original direct pointer lookups, with no
extra per-scalar branch or input pre-scan. Each cache initializes once per process when needed;
loading a model no longer eagerly constructs extended properties its pipeline may never use.

Normalization retains its compact generated data because it avoids much more expensive
normalization and casing calls. Most BMP properties are unchanged across Unicode 14–17.
The 87 BMP scalars whose relevant normalization properties changed are marked as requiring
the runtime. ASCII and stable BMP characters retain their SIMD and table paths. A conservative
union of non-trivial supplementary ranges prevents quick checks from incorrectly skipping
normalization on another supported runtime.

This avoids runtime version guessing and keeps table paths consistent with fallback paths.
The compatibility set compares general category, combining class, decomposition, and lowercase
across the official Unicode releases. It needs only UnicodeData.txt for each version; classification
no longer requires generated Alphabetic/Grapheme_Extend data. Source file checksums
are recorded in the generated Swift file; Unicode's data license is in `UNICODE-LICENSE.txt`.

## Validation

`swift test --filter Unicode` compares every BMP classification entry, every stable BMP
normalization property and mapping, and all non-trivial supplementary scalars with the runtime.
It also checks all version-dependent BMP characters through normalization and lowercase APIs,
including text that switches between fast and fallback paths. Comparisons use scalars or UTF-8
bytes: Swift String equality treats canonically equivalent spellings as equal and cannot
validate a normalization quick check. Failures report a code point instead of dumping tables.

The independent [Unicode conformance and upstream coverage audit](UPSTREAM_TESTS.md) records
the official Unicode 17 results, the Foundation defects and their fixes, and the remaining
differences from Python tokenizers. Runtime agreement alone is not proof of correctness.

CI runs debug and optimized tests on macOS 15 with Xcode 16.4 and macOS 26 with its default
Xcode, plus address and thread sanitizers. The iOS job retains the iOS 16 deployment floor.

### Lookup design and subsequent performance audit

Unicode properties are irregular data: a general arithmetic formula cannot replace their
tables. Arithmetic remains useful for regular subsets, including ASCII casing and Hangul
decomposition. Classification's existing direct table measured about six times faster than
runtime scalar classification in the multilingual lookup benchmark, so it is retained.
The cache now uses Swift's own Unicode data at initialization instead of a generated source
file. The extended-property builder also reuses general category to recognize letters as
Alphabetic, avoiding redundant property lookups.

BMP lowercase now uses a sparse 64-scalar page table of XOR deltas, replacing binary search.
An absent page shares the all-zero identity page. The payload is 8,064 bytes, compared with
131,072 bytes for a dense UInt16 map; lookup takes two indexed loads and one XOR. The mapping
is exhaustively checked for all 65,536 BMP values, including identity pages.

Three alternating release baseline/fixed runs on the same M2, with no concurrent builds,
measured the following medians of per-run mean API latency. Each sample repeats the benchmark
phrase 1,000 times; each run includes warmup and 15 timed iterations with output validation.

| Lowercase input | Binary search baseline | Sparse XOR mapping | Latency reduction |
|---|---:|---:|---:|
| ASCII | 0.094 ms | 0.093 ms | Within noise |
| Accented Latin capitals | 0.456 ms | 0.396 ms | 13% |
| Mixed scripts | 0.581 ms | 0.412 ms | 29% |

These are lowercase API measurements, not overall BPE throughput or evidence of being the
fastest tokenizer library. The corrected ICU fallback has a separate cost for text requiring
Unicode normalization; `UnicodeBenchmarkTests/forms` measures it explicitly. In one final
release run, decomposed-text NFC took 1.783 ms versus 1.244 ms through the old Foundation
property, and composed-text NFD took 3.111 ms versus 2.374 ms. This is a measured correctness
cost, not a speed improvement. Already-composed NFC retained its quick path (0.130 ms versus
0.461 ms through that property). These compare the current tokenizer API with the Foundation
property on the benchmark's valid inputs, not two full tokenizer revisions. Run all lookup,
lowercase, and normalization-form measurements with:

```sh
RUN_BENCHMARKS=1 swift test -c release --filter UnicodeBenchmarkTests
```

## Maintenance and performance

The classification generator and its 335-line, 34,367-byte generated source file have been
removed, along with the run-expansion helper. The two 64 KiB runtime caches remain, so memory
lookups in the scanners are unchanged. Generated normalization data remains: its 104,020
bytes of Swift source represent 31,808 bytes of numeric payload, plus 2,944 bytes for the
compatibility envelope. These are generated data, not hand-maintained per-character rules.

Three alternating release pairs on the M2 compared the original direct-cache hot path with
the final runtime-derived design using the same 200-paragraph Qwen stage benchmark:

| Operation | Before | Simplified | Interpretation |
|---|---:|---:|---|
| Qwen scanner | 0.671 ms | 0.657 ms | Similar throughput |
| Full cached BPE encode | 0.670 ms | 0.669 ms | Unchanged within noise |

Values are medians of three per-process means, each measured over 20 timed iterations after
warmup. The baseline executable used the same direct BMP lookup path; its cache was already
runtime-built for the construction experiment. How the identical cache is initially filled
does not affect these warm measurements. The baseline binary was preserved separately and
run alternately with the candidate; benchmarks did not overlap with builds.

The deliberate cost is at first use: three fresh processes measured median 2.404 ms to build
primary classification and 6.538 ms for extended properties, each once per process if needed.
Model loading no longer eagerly constructs the extended cache. Reusing the already-fetched
category for Alphabetic letters reduced combined construction from about 10.8 ms to 8.7 ms
in the repeated-construction benchmark. The original generated expansion measured 0.278 ms.

Removing normalization tables has a much larger recurring cost. Using the production BERT
fallback once for the whole input (rather than separately for every non-ASCII run) produced
identical bytes but measured 8.363 ms versus 0.720 ms for accented Latin, and 5.173 ms versus
0.523 ms for mixed scripts. This is why normalization tables remain. These are normalizer API
measurements on the fixed benchmark phrases repeated 1,000 times, not whole-model speedups.

An ASCII/BMP cache split was tried and rejected because it regressed the scanner benchmark.
The final code retains the original lookup branches and scanning loop. The compatibility
generator now uses five UnicodeData files instead of ten UCD files, and only 87 changing BMP
scalars instead of 139. Classification follows new runtime data automatically.

Final validation of this simplification passed the complete debug and release suites,
all 1,521,672 Unicode 17 conformance checks, and an independent word-property check for all
1,112,064 valid scalars. Focused Thread Sanitizer and Address Sanitizer runs passed 6 and
15 tests respectively; the iOS 16 simulator build and formatting checks also passed. CI's
sanitizer filters now include the classification caches explicitly.

Arithmetic still handles ASCII and Hangul. General casing, decomposition, and character
properties require Unicode's data; replacing the data with exception-filled arithmetic would
retain the maintenance obligation. See [UAX #15's optimization guidance](https://www.unicode.org/reports/tr15/tr15-57.html#Implementation_Notes)
and [UAX #44's derived-property definitions](https://www.unicode.org/reports/tr44/tr44-36.html#Property_Definitions).

To reproduce first-use timings, run only the selected test in a fresh process:

```sh
RUN_BENCHMARKS=1 UNICODE_COLD_BENCHMARK=1 \
  swift test -c release --filter UnicodeBenchmarkTests/classificationFirstUse
RUN_BENCHMARKS=1 swift test -c release --filter UnicodeBenchmarkTests/bertTables
```

## Regeneration

Download `UnicodeData.txt` from
`https://www.unicode.org/Public/<version>/ucd/` for versions 14.0.0, 15.0.0, 15.1.0, 16.0.0,
and 17.0.0 into `<ucd-dir>/<version>/`. Then run:

```sh
python3 scripts/unicode_compatibility.py --ucd-dir <ucd-dir>
python3 scripts/unicode_compatibility.py --ucd-dir <ucd-dir> --check
```

The generator uses only those input files, with no Python or host Unicode dependency.
Classification caches need no regeneration. To refresh the base normalization tables using
a supported Apple runtime:

```sh
REGENERATE_UNICODE_TABLES=1 swift test --filter UnicodeNormalizationTests
swift test --filter Unicode
```

When supporting a newer Unicode release, extend `VERSIONS` in the compatibility generator,
regenerate, and run the exhaustive checks on both older and newer runtimes. Do not replace
the baseline with newer tables alone: new data must be included in the compatibility envelope.
